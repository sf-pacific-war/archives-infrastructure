Design Proposal

Preservation-Led Digital Collections Asset Management

This proposal defines why shared drives and spreadsheets should not remain the long-term system of record for the archive, and why the preservation and asset management track must be designed as governed infrastructure. The target system separates canonical metadata, provenance, preservation files, access derivatives, federation, and AI/search layers so that collection growth does not destroy evidence or source meaning.

Decision Requested

Approve a dedicated preservation and asset management track, with Google Drive and Sheets limited to intake, coordination, and temporary staging.

System Boundary

Why Drive and Sheets are not a safe archival system.

Google Drive and Google Sheets are useful operating tools. They are not a preservation repository, archival database, rights-governance layer, or durable data model. The risk is not only inconvenience - the risk is losing original files, losing provenance, publishing restricted material, or making AI/search output look more authoritative than the source record.

Proposed role: Drive and Sheets can stay in the workflow as intake and collaboration surfaces. They should not be the long-term system of record.

No preservation boundary

Originals, access copies, edits, and exports can be mixed in the same folder. Without fixity, preservation events, and file-role controls, master files can be overwritten, renamed, duplicated, or lost.

No reliable provenance chain

Spreadsheet history is not a complete chain of custody. It does not reliably preserve who created a source description, when a file was received, how it changed, and which derivative was produced from which master.

No enforceable rights model

Access decisions cannot depend on ad hoc columns, folder names, or semantic similarity. Rights, restrictions, review status, embargoes, and publication state need governed fields and audit logs.

No real entity model

One row cannot safely carry collection context, object identity, source metadata, digital representation, stored file, and page or timestamp-level segments.

No federation strategy

Partner archives, universities, and national repositories need stable identifiers, APIs, export formats, source IDs, and mapping rules - not local-only spreadsheet conventions.

No safe AI boundary

OCR, transcripts, translations, summaries, and vectors are useful but derived. They must remain labeled, reviewable, rebuildable, and subordinate to source evidence.

P

Preservation track

Protect original and preservation master files with storage policy, checksums, versioned packages, preservation events, and auditable custody.

A

Asset management track

Manage relationships among objects, representations, files, derivatives, rights, and access copies so discovery and delivery can grow without corrupting the record.

Core Principles

Three foundation concepts for long-term digital asset management.

These principles come directly from the proposed design notes: preserve a canonical metadata layer, keep provenance explicit, and federate through APIs and standards without erasing source identity.

The architecture should make later search and AI stronger by making the underlying records more disciplined, not more blended.

Canonical Metadata

A governed, institution-approved source of truth for the fields the program is willing to claim: identity, hierarchy, rights, publication state, source context, and preservation status.

Entity Model

Do not flatten the archive into one spreadsheet row.

The core model separates ideas, descriptions, representations, files, and segments. Each entity has its own identity, lifecycle, relationships, and governance rules. This reflects the attached data-model proposal and the research framework for the current system.

The model is lightweight by design: enough structure to preserve truth, but not a heavyweight attempt to force every external standard into one local table.

C

Collection

Context, grouping, fonds, series, collection hierarchy.

O

Object

The cultural, historical, or knowledge object being described.

SR

Source Record

A description from a source institution, catalog, donor, or archivist.

DR

Digital Representation

How the object appears digitally: scan, audio, video, transcript, derivative.

F

File / Bitstream

The actual stored file, checksum, format, storage location, and file role.

S

Part / Segment

Specific page, region, clip, transcript span, or timestamp for citation.

Example model instance

Collection: Flying Tigers Historical Collection, including correspondence and audio from 1940-1945.

Object: Claire Chennault oral-history interview, 1944, subject: air war.

Representation: WAV preservation audio, MP3 access audio, and ASR transcript.

File: interview_master.wav with checksum 8a7b42f... for fixity verification.

Segment: page, region, or timestamp span, such as 00:13:14-00:14:22, for precise citation.

Why this separation matters

It prevents loss of original meaning and source differences.

It allows multiple descriptions for the same object.

It makes OCR, AI output, thumbnails, vectors, and access copies replaceable.

It supports precise citation down to page, region, transcript span, or timestamp.

Standards Ecosystem

Use a gear map, not a single winner standard.

The practical architecture should define a lightweight internal application profile and map external standards into it without loss. Each standard keeps its job. The canonical model coordinates them.

Strategy: define the internal canonical model first, then maintain versioned crosswalks for source import, partner export, and federation.

Dublin Core / DCMI

Broad cross-domain discovery and baseline metadata exchange.

MODS

Richer bibliographic and library-oriented structured description.

EAD

Archival hierarchy and finding-aid depth: fonds, series, files, items.

LIDO

Museum and material-culture object exchange, including complex object context.

PREMIS

Preservation metadata for files, events, agents, rights, and fixity evidence.

Metadata Detail

Relationships are first-class metadata, not notes in a cell.

Relationship modeling lets the system support authority resolution, multilingual discovery, precise citation, and explainable AI answers. It also keeps source descriptions separate from institution-approved assertions.

Ingestion and Federation Workflow

When a new file comes in, every stage should be auditable and reversible.

The workflow treats a new file as evidence first, then as a discoverable asset. It captures provenance and rights before enrichment, maps source metadata into the canonical model before federation, and allows AI to suggest derivatives without silently overwriting cataloger-controlled fields.

This is the operational bridge between preservation, asset management, metadata design, partner exchange, and downstream discovery.

1

Acquire / Harvest

Receive a file, partner package, upload, or harvested record with its source context.

2

Rights and Terms Gate

Check donor terms, provider restrictions, copyright, privacy, and access policy before processing.

3

Validate and Profile

Identify format, create checksums, inspect technical metadata, and reject unsafe or incomplete packages.

4

Canonical Mapping

Map source metadata into the internal model while retaining source-native fields and identifiers.

5

Normalize and Enrich

Create access formats, normalize dates and names, and prepare files for delivery or indexing.

6

Authority / Entity Reconciliation

Link people, organizations, places, events, and subjects to controlled entities where possible.

7

Deduplicate Relationships

Detect duplicates, versions, format variants, citations, and part-of relationships before publication.

8

OCR / ASR / AI Suggestions

Generate transcripts, OCR, summaries, topics, and embeddings as versioned derivative evidence.

9

QA / Human Review

Review rights, metadata quality, entity links, AI outputs, and search evidence before public release.

10

Publish Authoritatively

Publish approved records, delivery manifests, APIs, exports, and search indexes from the canonical layer.

Audit and rollback controls

  • Every stage records who acted, when it happened, what changed, and which source file or record was affected.
  • AI enrichments are versioned derivatives and never silently overwrite cataloger or rights-review fields.
  • Failed validation or rights uncertainty stops publication but preserves the evidence package for later review.

Federation outputs

  • Provider identity, source URL, source record ID, retrieval history, rights terms, and mapping provenance travel with the record.
  • Downstream APIs, IIIF manifests, OAI-PMH exports, and search indexes receive only the fields permitted by access policy.
  • Partner updates can be reconciled through source IDs and crosswalk versions instead of manual spreadsheet repair.
Search and AI

Hybrid retrieval constrained by structured facts.

Deterministic structured metadata governs access, dates, rights, and hierarchy. Probabilistic search improves discovery across text, language, and concepts. Both are necessary, but they must play different roles.

This boundary is the main control that makes AI useful without turning generated text into undocumented archival truth.

1.

Exact and fielded search

Best for identifiers, names, dates, rights states, collection filters, and known-item retrieval.

2.

Lexical search

BM25-style retrieval remains strong for rare names, historical wording, abbreviations, and exact phrases.

3.

Semantic search

Vector retrieval connects multilingual expressions, indirect mentions, and conceptually related materials across collections.

4.

Reranking and evidence package

Final ranking combines relevance, authority signals, and explicit evidence such as source record, page, region, or timestamp.

Must rely on structured canonical metadata

  • Rights and copyright control: never use semantic similarity to decide whether a restricted file is public.
  • Exact historical dates and source-institution attribution.
  • Archival hierarchy and context: fonds, series, file, item, segment.
  • File fixity, preservation events, and long-term storage status.

Appropriate for non-authoritative derived search

  • Full-text OCR and long-form oral-history transcripts.
  • Expanded essays, summaries, translations, and topic suggestions.
  • Regenerable semantic vector indexes for concept and multilingual discovery.
  • Reranking over evidence packages, never over detached chunks without source context.

Foundation Filters: Exact / Facets

Use canonical metadata for date ranges, rights, named entities, collections, formats, and publication state.

Lexical Retrieval: BM25

Use precise keyword matching for rare names, military unit codes, acronyms, and quoted phrases.

Semantic Retrieval: Dense Vectors

Use embeddings to capture conceptual similarity and multilingual variants that may not share exact vocabulary.

Reranking

Combine relevance, authority signals, and evidence references to improve the top results.

Success Factors

Evaluate the system as infrastructure, not as a prettier spreadsheet.

The pilot should be judged on governance, search quality, and preservation durability. These metrics translate the rough dashboard concept into measurable success criteria.

Search tests should include known-item queries and exploratory historical questions, with results evaluated against citation-bearing evidence.

Data Integrity and Provenance

Target 100%
  • Provenance coverage for published records should reach 100%.
  • All public records must carry explicit rights and access decisions.
  • Every derived record links back to source evidence.

AI and Discovery Accuracy

Pilot >=98%
  • Entity-link precision target: >=98% on reviewed pilot entities.
  • MRR measures known-item retrieval efficiency.
  • nDCG measures ranking quality for exploratory historical queries.

Digital Preservation Resilience

Fixity 100%
  • Scheduled fixity checks should pass for preservation files.
  • Storage forecast should cover the next 12 months of expected ingest.
  • Preservation copies must be separate from public access derivatives.
Implementation Path

Pilot the architecture before scaling the collection.

The first milestone should prove one representative collection end to end: intake, canonical modeling, preservation storage, derivatives, relationship metadata, search evaluation, and partner-ready export.

The proposal deliberately avoids big-bang migration. A small pilot can expose model gaps before the institution commits to a broader rollout.

Phase 1: Define and ingest

Select the pilot collection, assign stable IDs, define the canonical profile, capture preservation files, and generate fixity records.

Phase 2: Model and enrich

Create source records, representations, file relationships, segments, rights states, OCR/ASR/translations, and derivative metadata.

Phase 3: Test and federate

Evaluate retrieval with MRR and nDCG, validate provenance coverage, test IIIF/API/export paths, and document crosswalk decisions.
